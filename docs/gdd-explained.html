§ 01 The Premise · page 01 / 08

The agent does not get to decide what.

Two pictures dominate the conversation about AI writing software. Both hide the same question.

The first is the — a sidebar that completes lines and suggests refactors. You drive. It whispers. Copilot, IDE chat panels.

Plain version

An inline assistant lives inside your editor and only acts when you ask. It autocompletes, suggests refactors, answers questions about code you point at. It never opens files on its own.

The second is the — Jules, Devin, the various background coders. You hand it a prompt and walk away; later a PR appears. It decides a great deal of what to do.

Plain version

An autonomous agent is an AI worker you assign a task to and leave running. It picks its own files, writes its own code, opens its own pull request.

Both share an assumption: the agent is in charge of scope. It decides what files to touch, what to call done. Even the assistant picks the diagnosis the moment you say "fix it."

Scope is not a thing an agent is qualified to own.

GDD inverts this. The human declares the what. The agent figures out the how. The relationship is structurally asymmetric — what beats how.

The mechanism is a — a map of every unit of work, with prerequisites and a per-node definition of done.

What is a graph?

A dependency graph is a project plan drawn as boxes and arrows. Each box is a unit of work — a node. An arrow from A to B means "B can't start until A is done."

The agent doesn't invent the map. It receives one node, executes it, reports back. A human decides if truth has changed.

§ 02 The Apparatus · page 02 / 08

Two repositories, one doctrine.

The cast: two git repositories, one external agent, one human who alone can change the map.

gddp-config holds project truth — nodes, schemas, templates. Nothing runs here. Humans write; agents read. No exceptions. The first is a , which is just a directory tracked by git.

What is a repository?

A repository, or "repo," is a directory of files tracked by git. Splitting GDD into two repos puts a wall between things humans edit (truth) and things machines edit (state).

gddp-runtime is the machinery: a script that wakes on a schedule, reads the graph, finds work, dispatches it, records what comes back. It never edits project truth.

This separation is the whole game. Truth and activity live apart; activity never rewrites truth.

What a "node" looks like on disk

A node is a file. Inside you find what a well-written ticket would have, plus a few things it wouldn't.

YAML, briefly

YAML is a readable plain-text format for structured data. Indentation matters. Keys end in a colon. Lists start with a dash.

node_id: lead-intake
purpose: Capture landscaping lead information and normalize it into a project inquiry.
acceptance:
  # the conditions a human will check against
  - form accepts name, contact, project type, budget, location, timeline
  - submission creates one canonical Lead record
  - downstream estimator receives normalized project_type values
  - no duplicate client record is created
required_artifacts:
  - tests/lead-intake.test.ts
  - artifacts/node-runs/lead-intake/report.md
semantic_contracts:
  outputs: [Lead.created, EstimateInput.ready]
  must_not:
    - write directly to QuickBooks
    - create LMN proposal before consultation status

Two things matter. The node is a contract — it states what must hold true for the work to count. And the contract is written by a person before any agent reads it. Inheritance, not authorship.

The shape of every node is policed by a in the config repo.

Why a schema?

A schema is the rulebook for what a file is allowed to contain. gddp-config/schemas/v1/ holds one for every kind of object — node, job, result, event.

Acceptance vs. tests. Tests prove the code runs. Acceptance proves the code did what was asked. A function can pass tests while completing the wrong objective.

§ 03 The Forward Lane · page 03 / 08

How a node becomes a job.

The forward lane turns a written-down node into a unit of agent labor.

A script runs on a schedule, reads files, writes rows in a database, posts a GitHub issue. That's it.

At the center is the . Each tick asks the same questions.

Heartbeat, plainly

A heartbeat is a script that runs on a timer — say, every five minutes — and does the same checks each time. Cadence is a knob; the rhythm is the point.

What "ready" means

A node is ready when two conditions hold. Its own status is pending, and every node it has status: complete. If both are true, it is fair game for dispatch. If either fails, it sits.

Dependencies, plainly

A node's dependencies are the other nodes it lists as prerequisites. If B says "depends on: A," then A must be complete before B can be picked up.

Same logic as make. You cannot skip ahead.

What gets dispatched

The runtime builds a job packet — purpose, acceptance criteria, required artifacts, target repository, fresh job identifier.

An translates the packet into something the chosen executor understands. Today the only working adapter is jules_action_adapter.py, which opens a GitHub issue with the jules label.

Adapter, plainly

An adapter makes Agent X think the runtime is talking to it the way Agent X expects. New executor = new adapter, same core machinery.

Adding Codex or a local harness means a new adapter and nothing else.

Why state goes to a database

Every event, job, queue record, and result is written to a small file — db/queue.db.

SQLite, plainly

SQLite is a database whose entire contents live in a single file on disk. No server, no login. You inspect it with sqlite3 at the terminal.

Reason: auditability. The graph tells you what should happen. The database tells you what did.

Pull request? A PR is the standard way to propose changes in git — push a branch, ask to merge. In GDD, every successful job returns as a PR.

§ 04 The Return Lane · page 04 / 08

How a merged PR becomes a receipt.

Forward lane sends work out; return lane receives evidence back.

This lane stops on purpose, well before declaring anything complete.

The path, traced

A PR is merged. A hits the intake server and is signature-verified. A classifier parses the PR body and extracts the node and job identifiers. A return router builds a receipt with artifact references and writes a row to the results table.

Webhook, plainly

A webhook is a URL that another service (here, GitHub) hits with a JSON payload when something happens (here, a PR merging). Signature verification keeps strangers out.

What lives in a receipt

A is a row in the results table. It holds the job and node identifiers, the PR URL, paths to artifacts the agent produced, and a status — always needs_review at this stage.

Receipt vs. completion

A receipt says "the agent claims it did the work, here is the evidence." Completion is the output of a review, and only a human produces it.

The receipt is not a verdict. The runtime never makes verdicts. The receipt exists to be readable by the human who will.

Merging proves the code merged. Not that it did what was wanted.

The deliberate stop

An earlier version of this system treated a merged PR as proof of completion and auto-updated the graph. Wrong. Conflating merge with completion is the slip that fails agentic systems over time.

The return lane was severed from graph truth. The runtime stops at awaiting_review. Next move belongs to a human.

Frozen by design — receipts only; no auto-completion in this phase.

§ 05 The Truth Boundary · page 05 / 08

Five hands the operator can play.

When a job lands in awaiting_review, the runtime is finished with it.

The operator opens the PR, the receipt, and the node's acceptance criteria, and chooses exactly one of five named actions. All explicit. The boundary between activity and truth is drawn here.

ActionWhat it means
acceptThe work meets acceptance. The operator in gddp-config by hand and commits. Only path that moves the graph forward.
retrySomething failed but is salvageable. The job is re-dispatched, often with a sharper instruction.
blockThe work cannot move forward right now. Graph truth stays unchanged; blocker is recorded outside the runtime.
deferReceipt is fine, but acceptance isn't the right move yet — perhaps a sibling node needs to land first.
reopenLater evidence invalidates earlier work. The node is revisited or replaced; the graph is edited accordingly.
Why edit YAML by hand?

Editing the project graph is the act of saying "I accept this as truth." Removing that gesture would smuggle authority back into the runtime. The friction is the feature.

Why exactly five

The smallest vocabulary that covers every realistic review outcome without smuggling decisions into the runtime. None of these verbs is "the runtime decided." Accept, reject, defer — all belong to a person.

"Ignore" is not on the list. Doing nothing is defer — a real decision on a real desk.

The runtime is allowed to know what happened. Not what it means.

Reading a receipt in practice

Open the PR and read the diff. Read the receipt row in results. Walk through the node's acceptance list, one item at a time, checking each against the PR. Read the required artifacts.

If everything lines up — and only then — open the node's YAML and edit the status to complete in a hand-written commit.

Slower than automatic acceptance. That's the point — slowness is where judgment lives, and judgment is the load-bearing thing the agent cannot supply.

Known limit. The current return router has a hardcoded allowlist for skchaudr/vault-doctor. A scaling step is to lift that into config.

§ 06 The Operator's Drill · page 06 / 08

You learn the boundary by practicing it.

Reading tells you a system's shape. Practicing tells you what it feels like to be wrong about it.

Do these at a real terminal on a small real project. Answers come from files, rows, and receipts — not intuition. They're sequenced; later ones depend on earlier ones. None should take more than an evening.

  1. Synthetic Receipt DrillRun python3 scripts/init_db.py, then python3 scripts/dry_run.py. No real repo, no real agent. Inspect events, jobs, and results. Confirm the synthetic job ends in awaiting_review and no graph file changed.
  2. Forward Dispatch, Tiny Real RepoAdd a ready node to gddp-config for a low-stakes side project — a --dry-run flag, a missing unit test, a healthcheck endpoint. Run the heartbeat. Explain in words why that node was chosen and what was inside the packet.
  3. Receipt From a Merged PRTake the Run 2 job to completion: the agent opens a PR, you merge, the webhook fires, the receipt lands. Inspect the results row. Confirm receipt is needs_review, job is awaiting_review, no file in gddp-config changed.
  4. Human Accept DrillWalk through the acceptance criteria, one item at a time, against the merged PR. If everything matches, open the YAML and update status to complete by hand. Commit. Write down: what evidence made you comfortable accepting?
  5. Human Reject or Defer DrillRun the full lane with a PR that is intentionally incomplete. Receive the receipt, then choose one of retry, block, defer, or reopen. Do not touch the graph. Write down the exact condition that blocked acceptance.

Questions every run must answer

  • What created this job?
  • Why was this node selected?
  • What exactly was dispatched?
  • What did the executor return?
  • Where is the receipt?
  • Why is this job in awaiting_review?
  • What exact human action would change graph truth next?

If you can't answer all seven from files and rows — not memory — the drill isn't done. Repeat with a different tiny task. A fuzzy mental model becomes a system you can read.

Practice targets: one-file CLIs, tiny FastAPI apps, script repos. Avoid auth, migrations, payments. The drill is about the loop, not the change. Inspection is mostly one sqlite3 query or one find — keep deploy/BIGPI_RUNBOOK.md open in a scratch pane.

§ 07 What Comes Next · page 07 / 08

From local correctness to systemic meaning.

The next phase makes the graph not just the scheduler of work but the validator of meaning.

Treat this section as a road map, not a release.

The pivot: prove a function behaves. Acceptance proves a node delivered. Neither proves the project is still coherent.

Unit test, plainly

A unit test is a small piece of code that checks one function does what it claims. It is the cheapest signal that a single brick is square. It says nothing about the wall.

A node can pass its acceptance while quietly violating a that a downstream node was counting on. The next-generation runtime adds a stack of verifiers whose only job is to notice this drift.

Contract, plainly

A contract between two nodes is the promise the upstream one makes about its outputs and the downstream one makes about its inputs. When written down, an edge verifier can check it.

Why one verifier is not enough

A node adds a "send invoice" button. The builder writes it. Unit tests pass. Acceptance says "user can send an invoice"; it passes. But two nodes upstream, the graph promised an : no direct writes to QuickBooks before consultation.

Invariant, plainly

An invariant is a rule always supposed to be true, no matter what changes. "Every user has one primary email." Invariants are what make a system feel coherent over time.

The button writes directly to QuickBooks. A node verifier clears it. Only an edge or graph-invariant verifier notices. Traditional pipelines prove component correctness. GDD attempts .

Semantic correctness, plainly

Semantic correctness means the system did what it meant to do, not just what it was technically asked to do. A retrieval system returning "a discussion of the truth" instead of "the truth" is semantically incorrect — and passes every unit test.

The scaling stages

Stage 1

Single node, single agent

Where the system is now. One node picked manually. One agent. The operator runs the drills against it.

Stage 2

Multiple agents, one graph

Independent ready nodes dispatched in parallel. The graph says who owns which path.

Stage 3

Verifier agent added

A read-only agent reviews the diff, tests, and spec. Returns pass / fail / uncertain. Cannot edit code.

Stage 4

Dispatcher expansion

A scheduler reads the graph, opens panes in a multi-pane terminal like , injects prompts, watches reports, updates state.

Stage 5

Semantic graph gate

The project cannot be called done until a graph-level verifier confirms every completed node still satisfies upstream and downstream contracts. The gate turns "shipping" into a property of the system.

Beyond

OpenClaw & CI for meaning

A reasoning layer that surfaces uncertainty earlier and more legibly. CI/CD where the build target is a graph of meaning.

CMUX, briefly

CMUX is a multi-pane terminal built for running several agents side by side. In the next-phase sketch, it is the cockpit the dispatcher uses. The graph remains the source of truth.

Builders build. Verifiers verify. The graph decides what done means.

The non-negotiable thing

One rule doesn't move across stages: the agent doesn't decide if its own work passes. Verifiers make the human judgment cheaper and faster — they don't replace it.
