A field manual for the apparatus of bounded agent autonomy — written for the operator who would like to stop guessing.

There is a quiet revolution happening at the seam between humans and coding agents. This pamphlet is a teaching map of one attempt to make that seam load-bearing.

A system where the human owns intent, the agent owns labor, and a graph of dependencies sits between them as the contract.

Nothing in these pages is taken as understood. Words that sound technical can be expanded right where they appear — you don't need to know them yet.

§ 01 The Premise · page 01 / 08

The agent does not get to decide what.

When people say "AI is writing software now," they usually mean one of two pictures — and the two pictures, taken together, hide the question this manual is built around.

The first picture is the : a sidebar in your editor that completes lines and suggests refactors. You drive. It whispers. Copilot, the chat panel in your IDE — these are inline assistants. They never decide what file to open; you do.

Plain version

An inline assistant is an AI helper that lives inside your editor and only acts when you ask it to. It autocompletes lines, suggests refactors, answers questions about code you point at. It never opens files on its own. Copilot, Cursor's tab autocomplete, the chat sidebar — these are inline assistants.

The second picture is the : a service you hand a prompt to ("add user authentication to the marketing site") and walk away from. Some minutes or hours later, a pull request appears. Jules, Devin, the various background coders — these are autonomous agents. They decide a great deal of what to do.

Plain version

An autonomous agent is an AI worker you assign a task to and leave running. It picks its own files, writes its own code, opens its own pull request. Jules, Devin, OpenHands and similar tools — these all sit somewhere on this side of the line.

Both pictures share an assumption so quiet you can miss it: the agent is in charge of scope. The agent looks at the prompt, decides what files to touch, what to call done, what to leave for later. Even in the assistant case, the moment you say "fix it," the agent picks the diagnosis.

If an agent decides its own scope, it also gets to decide when it's done. That is a quiet conflict of interest. The whole design pressure of GDD is to take that authority away — gently, with paperwork.
Scope is not a thing an agent is qualified to own.

Graph-driven development — GDD — starts from a different posture. The human declares the what. The agent figures out the how. The relationship is not negotiated; it is structurally asymmetric. What always beats how.

The way this is made real is a — a written-down map of every meaningful unit of work in the project, with the prerequisites between them spelled out, and with each unit carrying its own definition of done.

What is a graph?

A dependency graph is a project plan drawn as boxes and arrows. Each box is a unit of work — here we call them nodes. An arrow from A to B means "B can't start until A is done." This is the same shape your build system or your kitchen routine has; we are just writing it down on purpose.

The agent does not invent the map. It receives one node at a time, executes it, and reports back. A human reads the report and decides whether truth has changed.

This pamphlet teaches the apparatus that makes that picture work, the boundary it refuses to cross, and the shape it is trying to grow into.

§ 02 The Apparatus · page 02 / 08

Two repositories, one doctrine.

The apparatus has a deliberately small footprint. Two git repositories sit at its center, plus an external agent that does the labor, plus a human who alone has the authority to change the map. That is the entire cast.

The first is called gddp-config. It holds the project truth — the graph of nodes, the schemas that describe what a node is, and the templates for writing new ones. Nothing in here runs. It is paperwork. Humans edit it. Agents read it but are not permitted to write to it.

What is a repository?

A repository, or "repo," is a directory of files tracked by git — a version-control tool that records every change. Splitting GDD into two repos is a way of putting a wall between things humans edit (truth) and things machines edit (state).

The second repository is called gddp-runtime. It is the moving machinery: a script that wakes up periodically, reads the graph, finds work, dispatches it to an agent, and writes down what comes back. It is the engine room. It never edits the project truth.

This separation is the whole game. Truth lives in one place. Activity lives in another. The activity never silently rewrites the truth.

What a "node" looks like on disk

A node is a file — a human-readable plain-text format with key/value pairs. Inside a node you find the things you would expect of a well-written ticket, and a few you might not.

YAML, briefly

YAML is one of the most readable plain-text formats for structured data. Indentation matters. Keys end in a colon. Lists start with a dash. It is what most modern config files use because both humans and programs can read it without ceremony.

node_id: lead-intake
purpose: Capture landscaping lead information and normalize it into a project inquiry.
acceptance:
  # the conditions a human will check against
  - form accepts name, contact, project type, budget, location, timeline
  - submission creates one canonical Lead record
  - downstream estimator receives normalized project_type values
  - no duplicate client record is created
required_artifacts:
  - tests/lead-intake.test.ts
  - artifacts/node-runs/lead-intake/report.md
semantic_contracts:
  outputs: [Lead.created, EstimateInput.ready]
  must_not:
    - write directly to QuickBooks
    - create LMN proposal before consultation status

Two things are worth noticing. First, the node is not just a task description — it is a small contract. It states what must hold true if the work is to count. Second, the contract is written by a person before any agent reads it. The agent inherits the contract; it does not author it.

The shape of every node is policed by a that lives alongside it in the config repo.

Why a schema?

A schema is the rulebook for what a file is allowed to contain. gddp-config/schemas/v1/ holds one for every kind of object — node, job, result, event. Without schemas, every node would drift into its own shape and the runtime could not safely read them.

Acceptance vs. tests. Tests prove the code runs correctly. Acceptance criteria prove the code did what the project wanted. They are not the same. A function can pass tests while completing the wrong objective — this is the whole reason humans stay in the loop.

§ 03 The Forward Lane · page 03 / 08

How a node becomes a job.

The forward lane is the part of the system that takes a written-down node and turns it into a unit of agent labor.

There is no magic here — it is a script that runs on a schedule, reads files, writes rows in a database, and posts an issue on GitHub. We will follow it step by step.

At the center of the forward lane is what the system calls the . Each tick asks the same small questions and acts on the answers.

Heartbeat, plainly

A heartbeat is a script that runs on a timer — say, every five minutes — and does the same checks each time. It is the opposite of an always-on, event-driven service: it doesn't react instantly, it just visits the system regularly. Cadence is a knob; the rhythm is the point.

What a "ready node" actually means

A node is ready when two conditions hold at the same time. Condition one: its own status is pending — nobody has marked it done yet. Condition two: every node it has status: complete. If both are true, it is fair game for dispatch. If either fails, it sits.

Dependencies, plainly

A node's dependencies are the other nodes it lists as prerequisites. If node B says "depends on: A," then A must be marked complete before B can be picked up. This is what makes the graph a graph instead of a list.

This is the same logic a build system like make uses, and the same logic a kitchen uses: the sauce can simmer once the stock is reduced; the plating can happen once the sauce is on. You cannot skip ahead.

What gets dispatched

The runtime does not ship the entire node to the agent. It builds a smaller object — a job packet — that contains the node's purpose, its acceptance criteria, its required artifacts, the target repository, and a fresh job identifier.

An then translates that packet into something the chosen executor understands. Today the only working adapter is jules_action_adapter.py, which opens a GitHub issue with the jules label — that label is what wakes Jules up.

Adapter, plainly

An adapter is a thin file whose only job is to make Agent X think the runtime is talking to it the way Agent X expects to be talked to. New executor = new adapter, same core machinery. This is the seam that keeps the design portable.

If tomorrow you wanted to dispatch to Codex, or to a local terminal harness, or to a yet-to-exist agent, you would write a new adapter and the rest of the system would not change.

Why state goes to a database

Every event, every job, every queue record, every result is also written to a small database file — db/queue.db.

SQLite, plainly

SQLite is a database whose entire contents live in a single file on disk. No server. No login. You can inspect it from the command line. It is the right size for a system meant to be readable by one person sitting at a laptop.

The reason it exists is auditability. Six weeks from now, if someone asks "why did this job exist at all?", the answer is one query away. The graph tells you what should happen. The database tells you what did.

Pull request? A pull request (PR) is the standard way to propose changes to a git repository: you push a branch and ask the maintainer to merge it. In GDD, every job that succeeds shows up as a PR — there is no other return surface.

§ 04 The Return Lane · page 04 / 08

How a merged PR becomes a receipt.

If the forward lane is "the system sending work out," the return lane is "the system receiving evidence back."

This is the part of GDD that took the longest to get right — and the part that the rest of the design now leans on. The whole point of this lane is that it stops on purpose, well before declaring anything complete.

Here is what happens, end to end, when an agent finishes a job and the resulting pull request is merged in the project's repository.

The path, traced

A PR is merged. A hits the intake server and is signature-verified. A classifier parses the PR body and extracts the node and job identifiers. A return router builds a receipt with artifact references and writes a row to the results table.

Webhook, plainly

A webhook is a URL that another service (here, GitHub) will hit with a JSON payload when something happens (here, a PR merging). It is how external events get into the system. The intake server verifies the signature so it can trust the payload came from GitHub and not from a stranger on the internet.

What lives in a receipt

A is a row in the results table of the SQLite database. It is the structured memory of "an agent finished something and these are its links." A receipt holds the job identifier, the node identifier, the PR URL, paths to artifacts the agent produced (test files, screenshots, reports), and a status that — at this point in the system — is always needs_review.

Receipt vs. completion

A receipt says "the agent claims it did the work, here is the evidence." It is the input to a review. Completion is the output of that review, and only a human can produce it. Confusing the two is the slip that takes agentic systems down.

The receipt is not a verdict. The runtime never makes verdicts. The receipt's whole job is to be readable by the human who is about to make one.

Merging a PR proves the code merged. It does not prove the code did what the project wanted.

The deliberate stop

In an earlier version of this system, a merged PR was treated as proof that a node was complete, and the runtime would obligingly update the project graph in gddp-config to mark it so. That turned out to be wrong, in a quiet and lasting way. The two are not the same, and treating them as the same is exactly the slip that makes agentic systems fall over in the long run.

So the return lane was severed from graph truth. The runtime now stops at awaiting_review. The next move belongs to a human.

Frozen by design — this is the part of the contract that does not change in the current phase. Receipts, no auto-completion. Restraint as load-bearing infrastructure.

§ 05 The Truth Boundary · page 05 / 08

Five hands the operator can play.

When a job lands in awaiting_review, the runtime is finished with it.

The operator now sits down with the PR, the receipt, and the node's acceptance criteria, and chooses exactly one of five named actions. None of these is automatic; all of them are explicit. The boundary between activity and truth is drawn here, in human hands.

ActionWhat it means
accept The work meets acceptance. The operator and commits the status change. This is the only path that moves the graph forward.
retry Something failed but the work is salvageable. The job is re-dispatched from its persisted state, often with a sharper instruction.
block The work cannot move forward right now. Graph truth stays unchanged; the blocker is recorded outside the runtime so future operators understand the stall.
defer The receipt is fine, but acceptance is not the right move yet — perhaps a sibling node needs to land first. The job sits in awaiting_review deliberately.
reopen Later evidence — a downstream failure, a new constraint — invalidates earlier work. The node is revisited or replaced, the graph edited accordingly.
Why edit YAML by hand?

Because the act of editing the project graph is the act of saying "I accept this as truth." Removing that gesture would smuggle authority back into the runtime. The friction is the feature.

Why exactly five

The five-action set is not arbitrary. It is the smallest vocabulary that lets an operator describe every realistic outcome of a review without sneaking decisions into the runtime. Notice that none of them is "the runtime decided to accept." That option does not exist in this phase. The runtime cannot accept, cannot reject, cannot defer — those verbs belong to a person.

Notice also that "ignore" is not on the list. Once a job is in awaiting_review, doing nothing is itself a decision: it is defer. Naming it matters, because deferred work is real work — it is still on the operator's desk.

The runtime is allowed to know what happened. It is not allowed to know what it means.

Reading a receipt in practice

The operator's actual workflow looks like this: open the PR and read the diff. Read the receipt row in results to see what the agent claims it did. Walk through the node's acceptance list, one item at a time, and check each one against the PR. Read the required artifacts the agent was supposed to produce.

If everything lines up — and only then — open the node's YAML and edit the status to complete in a hand-written commit.

This is slower than letting the runtime do it automatically. That is the entire point. The slowness is where judgment lives, and judgment is the load-bearing thing the agent cannot supply.

A known limit. The current return router has a hardcoded allowlist for one project repository, skchaudr/vault-doctor. A scaling step is to lift that allowlist into config. Documented openly so nobody is surprised by it.

§ 06 The Operator's Drill · page 06 / 08

You learn the boundary by practicing it.

Reading about a system tells you its shape. Practicing the system tells you what it actually feels like to be wrong about it.

The drills below are designed to be done at a real terminal, on a small real project, with the intent of producing answers from files, database rows, and receipts — not from intuition. They are sequenced; later ones depend on earlier ones. None of them should take more than an evening.

  1. Synthetic Receipt Drill Run python3 scripts/init_db.py and then python3 scripts/dry_run.py. No real repo, no real agent — just the system pretending. Inspect the events, jobs, and results tables. Confirm the synthetic job ends in awaiting_review and no graph file changed. The goal is to learn the filesystem and database shape with the lights on.
  2. Forward Dispatch on a Tiny Real Repo Add a small ready node to gddp-config for a low-stakes side project — a --dry-run flag, a missing unit test, a healthcheck endpoint. Run the heartbeat against it. Watch a real job get created and a real GitHub issue appear. Be able to explain, in words, why that node was chosen and what was inside the packet.
  3. Receipt From a Merged PR Take the job from Run 2 to completion: the agent opens a PR, you merge it, the webhook fires, the receipt lands. Inspect the results row. Confirm receipt status is needs_review, the job is awaiting_review, and no file in gddp-config has changed. This is the moment the deliberate stop becomes tangible.
  4. Human Accept Drill Walk through the acceptance criteria of the node, one item at a time, against the merged PR. If everything matches, open the node's YAML and update its status to complete by hand. Commit. Then write down: what evidence made you comfortable accepting? This question is the drill.
  5. Human Reject or Defer Drill Run the full lane with a PR that is intentionally incomplete or weakly tested — your call. Receive the receipt, then choose one of retry, block, defer, or reopen. Do not touch the graph. Write down the exact condition that blocked acceptance and the minimum next action that would unblock it.

The questions every run must answer

  • What created this job?
  • Why was this node selected?
  • What exactly was dispatched?
  • What did the executor return?
  • Where is the receipt?
  • Why is this job in awaiting_review?
  • What exact human action would change graph truth next?

If you cannot answer all seven from files and rows — not from memory — the drill is not yet done. Repeat with a different tiny task until the answers come quickly. The point of the drill is to replace a fuzzy mental model with a system you can read.

Practice targets: one-file CLIs, tiny FastAPI apps, a script repo. Avoid auth, database migrations, payment APIs, anything you would regret breaking. The drill is about the loop, not the change. Most inspection is one sqlite3 query or one find — keep the runbook (deploy/BIGPI_RUNBOOK.md) open in a scratch pane while you drill.

§ 07 What Comes Next · page 07 / 08

From local correctness to systemic meaning.

The system as described stops at the truth boundary on purpose. The next phase, drafted but not yet built, tries to do something more ambitious — to make the graph not only the scheduler of work, but also the validator of meaning.

Treat this section as a road map, not a release.

The pivot is simple to state and large to execute: tell you a single function behaves. Acceptance criteria tell you a single node delivered what was asked. But neither tells you the whole project is still coherent.

Unit test, plainly

A unit test is a small piece of code that checks one function does what it claims. It is the cheapest signal that a single brick is square. It says nothing about the wall.

A node can pass its acceptance while quietly violating a that a downstream node was counting on. The next-generation runtime adds a stack of verifiers whose only job is to notice this drift before it accumulates.

Contract, plainly

A contract between two nodes is the promise the upstream one makes about its outputs and the downstream one makes about its inputs. When the contract is written down, an edge verifier can check it.

Why one verifier is not enough

Imagine a node that adds a "send invoice" button. The builder writes the button. The unit tests pass. The node's acceptance says "user can send an invoice"; it passes. But two nodes upstream, the graph promised an : no direct writes to QuickBooks before the consultation phase is complete.

Invariant, plainly

An invariant is a rule that is always supposed to be true, no matter what else changes. "Every user has exactly one primary email." "No node may write to QuickBooks before consultation." Invariants are what make a system feel coherent over time.

The button writes directly to QuickBooks. A node verifier would clear this. Only a verifier that knows about the edges and graph invariants would notice. This is what the manifesto means when it says, "Traditional pipelines prove component correctness. Graph-driven development attempts to prove ."

Semantic correctness, plainly

Semantic correctness means the system did what it meant to do, not just what it was technically asked to do. A retrieval system returning "a discussion of the truth" instead of "the truth" is semantically incorrect — and passes every unit test.

The scaling stages, plainly

Stage 1

Single node, single agent

Where the system is now. One node picked manually. One agent. The operator runs the practice drills against it.

Stage 2

Multiple agents, one graph

Independent ready nodes are dispatched in parallel. Agents do not overlap because the graph says who owns which path.

Stage 3

Verifier agent added

A separate read-only agent reviews the diff, the tests, the node spec, and returns pass / fail / uncertain. It cannot edit code; it can only judge.

Stage 4

Dispatcher / runtime expansion

A scheduler reads the graph, finds ready nodes, opens panes (in a multi-pane terminal like ), injects prompts, watches reports, updates state.

Stage 5

Semantic graph gate

The project cannot be called "done" until a graph-level verifier confirms every completed node still satisfies its upstream and downstream contracts. This is the gate that turns "shipping" into a property of the system, not a vibe.

Beyond

OpenClaw & CI for meaning

A reasoning layer that surfaces uncertainty to the human earlier and more legibly. CI/CD for agentic systems, where the build target is a graph of meaning, not just compiled bytes.

CMUX, briefly

CMUX is a multi-pane terminal built for running several agents side by side, with workspace and notification hooks. In the next-phase sketch, it is the cockpit the dispatcher uses to open and watch agent panes. The graph remains the source of truth; CMUX is just the surface.

Builders build. Verifiers verify. The graph decides what done means. You decide what the graph means.

The non-negotiable thing

Across every stage, one rule does not move: the agent does not decide if its own work passes. Every additional verifier is a way of making the final human judgment cheaper, faster, and easier to escalate to — not a way of replacing it.

That is the bet of the next phase: that with the right ladder of read-only verifiers under it, the human review at the top becomes the strongest version of itself — the only place where systemic intent actually lives.
